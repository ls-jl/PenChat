# Y07 扫描白灯修正 · 0.2.26

## 原因与修正

Y07 的 `/sys/class/leds/flash-led-gpio/brightness` 不能按通用 LED
亮度范围理解。设备自带 `/usr/bin/len_onoff.sh` 在 `RK3562_Y07_V0`
分支使用 `1` 开白灯、`127` 开红外灯、`0` 关闭。
0.2.25 误用 `255`；写入成功或读回亮度不能证明实际白灯亮起。

0.2.26 在独立 Y07 采集配置中记录白灯模式值 `1`，硬件控制读取该值。
继续使用 LED 类接口，不导出、抢占或解绑 GPIO，不修改系统配置和驱动。
ORANGE 与 Y02 原有控制路径不变；原有租约在退出、错误和父进程恢复时
继续关闭灯并恢复快照、V4L2 格式及系统采集进程。

`/usr/configs/hal_led_config.json`、旧 HAL GPIO 路径与当前设备树并非
可互换的控制接口；不能仅凭表内 GPIO44 改写当前驱动拥有的引脚。
这次依据实际系统控制脚本及物理确认修正，而非根据最大亮度猜测。

## 硬件证据

- 用户已明确确认白灯亮起。
- 已查看修正后的真实 752×440 原帧，不再是黑场；此前灰度中位数约8，
  修正后约126，5%与95%分位分别为17、165。
- 连续20次独立硬件租约，每次读取24帧，均无序号缺口；每次结束后灯为0。
  最后系统 `CaptureFrame` 恢复，MiniApp 宿主 PID 始终为273，未重启宿主。
- 原帧和日志存于忽略的 `.work/y07-light/`，不进入源码仓库。

上述验证证明白灯和原帧链路恢复，不代表白纸增益校准或正向文字长扫
已验收；扫描中性校准的既有边界不变。照片相机黑场也不能由此判定解决。

## 真实划扫发现的第二个故障

白灯恢复后，真实笔头划扫进入首批推理，系统RKNN 1.4.0报
`Meet unsupported maxpool attribute 'dilations'` 并触发SIGABRT（信号6）。
扫描进程死亡释放EVIOCGRAB后，后续笔头事件由系统扫描响应，表现为“没有抢过按键”。
真实按键记录及独立采集已确认事件为led_control/134，不是另一机身侧键。
此前黑场过滤掉全部帧，未执行推理，因此20次空结果采集循环不能证明NPU可用。

Y07改用应用内独立RKNN 1.6.0，官方提交
`b25dadacc24b88eb7dfcaa47c9c525ecca89b319`；完整库SHA-256锁定在扫描依赖锁中。
不覆盖设备系统库，ORANGE/Y02继续使用原系统运行库。目标设备上已连续完成3批
固定32帧模型推理，每批返回9个输出，未触发旧错误。

该闭源库导入system。Y07内核不支持所需seccomp过滤，因此最终实现不是seccomp：
扫描可执行文件通过dynamic-list导出拒绝执行的同名函数，vendor导入在libc之前
绑定到该函数，返回ENOTSUP，不读取/记录参数、不创建进程。动态测试库验证
调用不会成功执行命令；真实RKNN在相同阻断下仍完成3批推理。
包检查仅对这份精确校验值的库及扫描可执行文件中的已定义阻断符号作窄例外，
其他system导入、popen、shell路径及命令入口仍禁止。

RKNN二进制继续保持Git忽略，其使用/再分发未授权状态见第三方声明；没有发布服务器文件。

- 主机核心CTest：14项通过，反馈物理键测试按环境跳过1项；JS 34项通过。
- 扫描8项CTest、真实子进程与Y02原尺寸模拟、LVGL扫描确认/丢弃/让渡回归通过。
- 扫描8项ASAN/UBSan通过；使用项目规定的有限quarantine配置。最初未设置该配置
  的执行被RSS保护拒绝，不将其计为通过。
- 新装隔离数据库、运行命令策略、退出清理、竖屏编辑/裁剪回归通过。
- AArch64构建、依赖/许可证/身份/strip和AMR校验通过；环境检查仅建议可选cnpm。
- ARM64设备动态测试库确认system导入绑定拒绝执行函数，返回ENOTSUP；
  带同一阻断的真实RKNN 1.6.0连续3批推理通过，退出码0。
- 已安装Y07，系统宿主保持PID273；未覆盖系统运行库，真实文字长扫最终结果待用户确认。
- 中间的自动化设备流程在用户发现扫描子进程退出后主动中断并走finally恢复原数据，
  不将该流程记为完成。随后独立物理划扫复现并定位SIGABRT，才形成最终修正。
