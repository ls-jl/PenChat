# Y02：NPU 大块内存操作与采集停顿定位

这是此前[驱动连续性检查](Y02-DRIVER-AUDIT-2026-11-05.md)的后续后台实验。
本轮不修改产品、扫描算法、模型、数据库或系统驱动，也不重新安装应用。

## 已确认的位置

已从“模型初始化附近”缩小到 NPU DRM GEM 内存接口：

| 操作 | 实测 ioctl | 对象 |
|---|---|---|
| 创建 | `0xc0286442`，MEM_CREATE | 60MiB，flags=`0x3`，非连续、可缓存 |
| 同步 | `0xc0206445`，MEM_SYNC | 同一对象的 TO_DEVICE 缓存同步 |
| 销毁 | `0xc0106444`，MEM_DESTROY | 同一对象 |

这块60MiB对象是运行库内部工作缓冲，不是应用的5.625MiB输入特征数组。
本轮只在独立探针内复制其内存操作，不减少或改写产品四项模型缓冲。
已安装内核的符号表存在`rknpu_gem_create_ioctl`、`rknpu_gem_sync_ioctl`和
`rknpu_gem_object_destroy`，所以不是把DMA-heap接口误认成DRM接口。

直接操作上述对象，不加载RKNN运行库、不读取模型、不执行推理、不做图像筛选或拼接，
仍能复现原始序列缺口。因此触发条件不要求运行模型算法，
不能将这些缺口归为模型几何解算、应用复制图像或NPU输出解析错误。

## 测试方法

- 使用原有硬件租约，独立采集进程；不访问用户聊天数据库，不保存或上传像素。
- 所有测试在后台，不打开PenChat页面或键盘，不请求API，不重启MiniApp宿主。
- 临时可执行程序导出`ioctl/mmap/mmap64/munmap`计时包装，最终仍调用同一内核系统调用。
  包装只保存请求码、长度、参数标志和时间，使用有界预分配记录，不在调用中分配JSON或写文件。
  同时链接产品的命令执行阻断器，不修改厂商库。
- 原始出队跟踪仍只观察AIQ线程，不调用它的DQBUF、不取走它的帧。
  配对使用原始与NV12输出逐位相同的源时间戳。ptrace有观察开销，不能拿其丢帧率代表日常使用。
- 后续队列和调度试验不使用ptrace；只读QUERYBUF不会排队、出队或改变缓冲状态。
  四只缓冲的查询是顺序观测而非原子快照，重点检查持续多次的状态，不据单次读数推断瞬时内部链表。
- CPU上下限临时固定600MHz并恢复；各组均记录NPU/DMC实际频率。
  不同内存频率的组不作为无控制的“修复前后”性能比较。

## 绕开模型的最小重放

依次执行创建、获取映射偏移、mmap、CPU清零、缓存同步、munmap、销毁，
每步之间等待约0.75秒（实际调度后更长），共3轮。
这使创建和同步之间、同步和销毁之间的缺口不会被混为一个初始化阶段。

在CPU600MHz、NPU300MHz、DMC324MHz的这一组中：

- 27.86秒收到3283帧，9次断档、实际缺25帧；驱动输入loss增量43，输出loss为0。
- 原始跟踪窗口3209/3209正常输出帧全部配对；9个缺口均无中间原始出队帧。
- 三轮创建均对应5～6帧缺口；创建调用耗时247～268ms。
- 三轮缓存同步均对应1帧缺口；同步调用耗时19～23ms。
- 三轮销毁均对应1～2帧缺口；销毁调用耗时162～190ms。
- 这一组未在mmap、CPU清零或munmap步骤捕获缺口。

源缺口经常延续至驱动调用返回之后，不能把“前一帧至后一帧”的整段时间都算作内核调用时间。
这里的对应关系包含回收和管线恢复延迟，而非声称整个缺口严格包含于一次ioctl。

## 实时唤醒对照：不是普通用户态忙计算

将NPU内存操作线程单独固定CPU3，维持普通调度策略；另在CPU0和CPU3各放一个
每次仅记录时间再休眠1ms的有界探针。探针使用RR21，优先级高于设备实际AIQ的RR20。
实际读取AIQ线程stat确认TX、RX及RawProc均为RR20，不仅依据SDK默认值推断。

CPU600MHz、NPU800MHz、DMC1272MHz，三轮操作的RR21结果：

| 同核操作 | 调用耗时 | CPU3唤醒间隔最大值，逐轮 |
|---|---:|---:|
| 创建60MiB对象 | 134～143ms | 46.88 / 51.16 / 53.24ms |
| 同步60MiB对象 | 12.3～14.5ms | 12.92 / 15.14 / 15.15ms |
| 销毁60MiB对象 | 96.2～98.0ms | 16.01 / 17.88 / 18.03ms |
| mmap、munmap及CPU清零对照 | 分别约13、18、51ms | 约3.3～3.6ms |

CPU0整个测试最大唤醒间隔3.81ms。该固件休眠1ms后的通常调度粒度约3.3ms，
所以这些值是完整唤醒间隔，不是扣除正常定时粒度后的额外阻塞时间。
同样的CPU清零持续约51ms，但实时探针可以正常抢占；驱动创建和同步期间则出现长停顿。
该组采集3181帧无断档，说明同核调度停顿本身不保证每次都造成丢帧：
AIQ还可能在其他核获得运行机会。不能把固定单核和高内存频率下的结果当成所有设备状态均无问题。

设备版本字符串没有PREEMPT，符号表有`_cond_resched`而无`preempt_schedule`。
本地词典笔参考defconfig为`CONFIG_PREEMPT_VOLUNTARY=y`。
这与实测“普通优先级的长内核操作阻止同核RR21及时运行”相符，
支持非完整内核抢占条件下长驱动处理导致调度停顿，而非仅仅用户态计算优先级过高。
没有读取到设备实际完整.config，因此不把参考defconfig宣称为固件逐字配置。

### 缓存同步分段对照

在同一进程、同一60MiB对象和相同频率下，分别重新清零对象，再比较单次同步与
按offset连续同步30段、每段2MiB。保持TO_DEVICE方向，不省略范围，也不增加或减少模型缓冲。
3轮结果均成功，32.58秒收到3863帧无断档：

| 方式 | 每轮同步系统调用总耗时 | 单次调用最长 | CPU3 RR21最大唤醒间隔 |
|---|---:|---:|---:|
| 一次60MiB | 14.20～14.33ms | 14.20～14.33ms | 14.93～14.97ms |
| 30次2MiB | 21.97～22.08ms | 0.89～0.99ms | 3.68～3.70ms |

分段增加了总耗时，但显著缩短无法及时运行实时探针的窗口；
它比单纯提高用户态优先级或减少CPU清零量更直接地验证了长驱动调用边界的影响。
这不是已交付的运行库改造，不能未经实际模型输出、取消、缓存方向及运行库线程语义验证，
就将临时包装器加入生产程序。

## 原始缓冲周转证据与限制

不跟踪AIQ、只读查询其四个原始缓冲，另一组27.57秒采集3259帧、4次断档、实际缺11帧。
多次连续采样在缺口附近显示3只缓冲已出队、仅1只仍为QUEUED/ACTIVE，
例如同样三只缓冲维持已出队状态超过20ms；这不足以持续维持双缓冲采集和后端处理。
不是应用NV12端12只缓冲耗尽，也没有新增CSI物理链路错误来解释这些缺口。

“CIF出队前已缺帧”不等于AIQ的周转与调度完全无关：
AIQ持有的原始帧不能及时处理和归还，同样会使CIF在出队之前失去可用缓冲。
QUERYBUF无法单独区分AIQ正在等待ISP完成，还是哪个具体工作线程尚未获得调度；
目前不将某一AIQ源代码行定为唯一根因。

另做了有意限制DMC至324MHz的压力实验。若在启动采集前限制，曾一次触发
“pen sensor did not deliver sustained frames”；改为稳定启动后限制，28.54秒内
出现263次断档、实际缺622帧，连没有NPU调用的空闲阶段也受影响，并观察到原始队列进一步耗尽。
这说明内存带宽余量也影响整个系统管线；它不是设备正常设置下的基准，
不能据此声称正常扫描一直固定在不足的DMC频率。实验后立即恢复原上下限。

## 能定位到哪一层

可以确认的最小故障边界是：**NPU GEM大对象内存处理的长调度停顿，以及原始采集缓冲的回收不足**。
缓存同步接口单独可重现停顿；创建和销毁路径也有更长停顿。

参考SDK的对应调用链为：

```text
rknpu_gem_create_ioctl
  -> rknpu_gem_object_create
  -> rknpu_gem_get_pages
  -> drm_gem_get_pages / dma_map_sg / IOMMU映射

rknpu_gem_sync_ioctl
  -> 遍历scatterlist
  -> dma_sync_single_range_for_device

rknpu_gem_object_destroy
  -> rknpu_gem_free_buf / rknpu_gem_put_pages
  -> dma_unmap_sg / 释放页面
```

flags=`0x3`使用非连续页分支，不能直接把它称为CMA连续内存分配失败。
设备驱动报告0.9.1，本地参考树为0.9.2；接口编码、flags和导出函数吻合，
但不能据此宣称每个内部实现都逐字相同。
设备无ftrace/perf和任务内核栈接口，本轮没有加载内核模块或修改驱动，
因此**尚未直接追踪到创建路径内究竟哪个子函数连续占用了那47～53ms**。
这条边界必须保留，不能将参考源码中的`dma_map_sg`某行冒充已实测的唯一故障行。

## 后续修复约束

1. 首次模型创建、映射和预热应尽量在打开/接受采集之前完成；健康模型继续常驻。
   退出仍须先停采集，再销毁模型。这不能单独保证解决后续所有扫描及光学对齐误差。
2. 缓存同步分段实验已验证可改善实时唤醒，同时增加总耗时；
   不能未经实际模型数值和运行库语义验证就拦截或省略供应商同步。
3. 若从内核修复，应使用相同固件源码，在长处理可安全调度的位置加抢占/重调度检查，
   或使用经验证的抢占配置。不可在持有自旋锁/关闭中断时盲目插入cond_resched。
4. 扩充原始池可增加容忍度，但不是恢复已丢像素，也不能代替修复长停顿。
   本轮未改系统AIQ池大小、AIQ线程/IRQ亲和性或模型四项缓冲；仅对独立探针设置过CPU亲和性。

所有完整日志、探针、原始队列采样和临时适配代码保留在忽略目录，不进入Git。
完成后恢复调试值及权限、CPU/DMC上下限和采集守护，退出观察线程并删除设备临时可执行程序。
