# 上下文压缩（自 0.1.23 起）

设置中的“自动上下文压缩”默认开启；加号菜单可手动“压缩上下文”或“查看上下文摘要”。
“查看上下文摘要”仅保留在加号菜单，使用开口文档轮廓图标；可查看覆盖终点、生成时间及对应的“压缩前副本”。聊天侧边不再额外放置摘要入口。
原消息、公开思考和原图仍然保留在当前会话中。此功能不减少本地聊天记录占用。

## 模型和预算

自0.2.5起，模型编辑页使用“最大上下文”，范围1,024～2,097,152。新增模型可按已核实的能力库预填，未知模型仍默认16,384；旧模型保留原本的本地预算，用户修改优先。它用于本地调度，估算结果不是精确计费或服务端tokenizer结果。
估算使用每三个 ASCII 字符一个 token、每个其他 Unicode 码点两个 token、每条消息 16 个
封装 token，以及每张图片 2,048 个 token。图片的 Base64 不作为普通文字计算。
对尚未覆盖的 Responses 不透明思考条目另预留每项 1,024 token；该估算不是精确的推理消耗。

设置中的全局“自动压缩阈值”默认75%，可设10%～95%。下一次发送前，包含待发内容的估算量达到“用户设置的最大上下文×阈值”才先压缩；目标是摘要、剩余历史、系统提示词和本次输入合计不超过最大上下文的 `min(50%, 阈值×2/3)`。阈值在任务开始时冻结。
优先保留最近四轮；若它们本身超出目标则扩大前缀范围。只在助手消息末尾切分覆盖范围，
待发送文字和最后一轮之后的待发送图片均不压缩。手动压缩可处理更短的历史。
没有可处理的助手回复时不发起摘要请求。

预设编辑中的“上下文压缩模型”默认为“跟随聊天模型”；选择另一预设时，留空会明确清除
上一预设指定的压缩模型。上拉新建继承该选择，历史菜单新建应用默认预设。
摘要及其覆盖范围属于原会话，不随新建复制。切换模型/预设不使既有有效摘要失效。

## 请求与失败

摘要请求使用现有 Responses、Chat Completions 或 Anthropic Messages，API 默认推理强度，不请求公开思考，也不带厂商思考开关。
整理指令只用于这次辅助请求；原会话提示词不用于整理历史。历史内容与已有摘要作为引用数据，
要求保留事实、约束、决定、未解决问题、失败/未完成状态及图片信息，不执行其中指令。
小预算模型按顺序分段，每段携带上一段摘要；整个操作只生成一份归档。

后续聊天把摘要作为普通用户角色的历史参考，之后跟未覆盖原文与本次输入；系统提示词仍只注入一次。
覆盖范围内的原图和加密思考条目不续传，原图保留在本地。模型能力显式声明 `vision:false` 时
拒绝带图片的压缩；未知能力由接口验证，拒绝后不换模型、不自动重试。

请求开始冻结聊天/压缩模型配置、输入及凭据；停止、切换会话、删除源会话或退出使旧结果失效。
压缩失败、摘要过长、模型失效或预算无法满足时，停止排队发送并保留草稿、图片和原上下文。
关闭自动压缩也会发送完整有效历史；超过本地预算则明确报错，不悄悄截断。
历史准备上限为十万条且参与读取的文本/元数据不超过 32MiB；单张图片最大 16MiB，
单次请求（含估算编码图片）最大 64MiB，超过时明确报错。

## 事务与资产

没有数据库结构升级。`chat_sessions.metadata_json.context_compression` 保存版本、摘要、覆盖 `seq`、
来源校验、修订号、时间和归档 ID。校验采用按消息角色、状态、顺序、正文和图片属性计算的
FNV-1a 64 位摘要，用于检测意外变化，不提供文件真实性或抗篡改保证。

先完成全部网络请求，校验压缩后图片能力、最大输入和资源限制，再在 DB 工作线程的一次事务中检查来源、复制完整会话和替换摘要。校验失败不留下摘要或归档。
消息、分段、资产和流事件均重新生成内部 ID；归档状态为 archived，标题前缀“压缩前副本”。
私有图片文件共享，不重新复制；现有资产引用检查及压缩任务租约防止误回收。
事务失败或来源过期会整体回滚。每次成功都保留一份归档，不自动删除。

归档还原只将该副本恢复到活动列表，不覆盖继续进行的会话。查看对应归档会定位到归档列表，保留当前草稿和阅读位置；归档删除后摘要仍可继续使用。

## 备份兼容

聊天包可携带公开摘要、覆盖范围和压缩模型描述，不包含加密续传条目或凭据。
压缩前副本作为普通归档会话选择导出。预设包可携带独立压缩模型描述，沿用接口地址、类型和
模型名的唯一匹配规则。缺失模型保留为待配置，不自动创建 Provider。
导入预览检查语义覆盖校验；缺失附件或范围不匹配时保留完整历史、停用摘要并提示重新压缩。
导入重新生成 ID、重建图片路径，已验证的校验重新绑定到导入后的记录，不保留无效的旧归档 ID。

### 已确认的代码行为与本地证据

`context.cpp::summarize()` 使用现有 `streamModelRound()`，但只读取
`response_state.output` 和 `done`，忽略 `network_error` 中已有的错误、HTTP 状态和
请求标识。因此 HTTP 400／429／5xx、传输失败、协议不完整以及非正常 finish reason
均可能只显示“上下文压缩失败，请检查网络或模型配置；未发送本次消息”。这是一项
已确认的诊断缺陷，并不意味着所有失败都来自网络。

以现有 `build/host/libpenchat_core.a` 链接独立 C++14 探针，通过本机假 HTTP 服务验证：

| 模拟情况 | 底层结果 | 压缩结果 |
| --- | --- | --- |
| 正常正文、stop、DONE | done | 成功生成摘要 |
| HTTP 400，含明确错误正文 | network_error，保留 HTTP 400 和原始测试原因 | 仅通用失败文案，具体原因丢失 |
| 正文存在，finish_reason 为 length | network_error，回复未完成：length | 仅通用失败文案，不能使用截断摘要 |
| 仅 reasoning_content，没有正文 | done，但正文为空 | 仅通用失败文案，不能把思考当作摘要 |
| stop 后关闭连接，缺少 DONE，严格模式 | network_error，Stream ended before completion | 仅通用失败文案 |

| 正常结束，但返回 8,000 个本地估算 token，摘要预算为 4,096 | done | 报“模型生成的摘要未满足预算”，原上下文不提交 |

### Gemini 相关线索与尚未证实的原因

- 压缩明确使用 API 默认强度，清空 `effort_value`，不请求公开思考；这不等于禁用
  模型内部思考。Google 的 [OpenAI 兼容说明](https://ai.google.dev/gemini-api/docs/openai)
  表明不传 reasoning_effort 时使用模型默认思考级别／预算，部分模型不支持关闭。
  因此默认思考可能增加延迟；是否导致这次超时、空正文或输出限制，须由实际错误证明。
- 本地 `summaryBudget` 目前写在整理提示词中，再对结果做估算校验；当前 OpenAI 兼容
  请求体没有据此发送输出 token 上限。模型正常返回但未遵守提示长度时，压缩仍会失败。
  不应简单把摘要预算原样作为 Gemini 的总输出上限：Google 的
  [思考 token 与输出限制说明](https://ai.google.dev/gemini-api/docs/generate-content/thinking)
  说明思考会消耗输出预算，过小上限可能造成截断甚至空正文。
- 分批使用压缩模型本地 context_budget 的 75%，没有在该分批处统一收敛到已配置的
  max_input_tokens。实际端点上下文／输出能力、图片估算及用户预算不一致时有被拒绝的风险；
  目前没有该用户请求的证据，不能把它认定为已发生。
- 历史整理材料保留原 user／assistant 线角色，并只对 Anthropic 做统一 user 引用处理。
  探针确认本次末条为 assistant；某些兼容网关的角色／续写约束仍需核对。
  不将“Gemini 一律不接受末条 assistant”当作已确认事实。
- 当前只有 Responses、Chat Completions 和 Anthropic Messages；没有 Gemini 原生
  generateContent 协议。需核对用户选择的接口与实际地址，而非按模型名自动改 URL、
  协议、强度或 Provider。
