# 上下文压缩

## 当前开发实现

客户端文本压缩移植自 OpenAI Codex CLI `4389a526d51a5a7600e0648436a7142a304f0188` 的
`core/src/compact.rs`。来源文件校验与提交记录在
`native/lvgl-app/codex-compaction-source.json`；Apache-2.0 和上游 NOTICE 随包保留。

先以完整有效历史生成交接摘要，再保留最近的用户原话。摘要包含进展、决定、约束、偏好、
未解决问题和关键引用。压缩使用当前聊天模型或预设指定的压缩模型，通过 Responses、
Chat Completions 或 Messages 普通生成接口请求，使用 API 默认强度、关闭工具执行。
原始聊天、照片和公开检索记录保留在数据库中。

### 前缀选择与下一次请求

压缩模型装得下时一次总结全部可处理的完整历史。预算同时考虑模型的本地最大上下文、
最大输入、图片、指令及输出余量（最多 4096，至多窗口四分之一）；Messages 必需的输出
额度在辅助请求中限制于此余量。正常聊天请求的输出配置继续遵守用户设置。

装不下时，从最新端移出完整问答，选择可容纳的最长旧前缀。被移出的对话原样接回。
只有明确的输入超窗错误允许缩小前缀后请求；鉴权、限流、断流、截断、空摘要等直接失败。
单个完整问答或工具批次也超限时，指出无法容纳的单元，保留输入与已有检查点。

下一次请求的顺序为：

1. 已摘要范围内保留的用户原话，按时间排序。
2. 普通用户角色的历史参考交接摘要。
3. 未覆盖的完整原文和工具结果。
4. 本次待发送文字与图片。

原话从近向远选择，最多 20,000 个本地估算 token，并按剩余空间缩小。
这份额外副本可以保留首尾、明确标记中段省略。原始消息、本次输入和未覆盖原文完整保留。
若摘要加未覆盖内容仍超出聊天输入预算，继续将摘要与随后能容纳的完整旧单元合并。
同次操作每步推进覆盖边界，全部成功后仅创建一份压缩前归档。
不再强制保留四轮或要求摘要达到固定压缩百分比。

自动压缩继续默认开启，默认阈值 75%，设置范围 10%～95%。触发估算包括本次输入、
系统提示词及工具定义。原话的额外保留量优先使用阈值以内的空间。估算方法沿用应用的
本地保守估计，不能当作服务端 tokenizer 或计费统计。

### 压缩收益与小窗口精简

提交前按操作开始时的有效上下文检查收益，包括既有工具检查点及实际选中的回复路径。
删除图片和不透明状态的估算额度不计作收益。摘要、未覆盖原文和额外保留原话的可见文本
合计，至少节省可压缩文本的10%或32个估算token（取较大值）；保留原话也受此余量约束。
这是本地收益门槛，接口使用的tokenizer及图片计数可能不同，实际用量以服务返回为准。

当前前缀不足以产生收益时继续覆盖后续完整单元。所有单元处理后仍没有收益，手动压缩
提示保留原上下文；自动压缩在原输入仍满足预算时继续原请求，不创建摘要或归档。
原输入本身超限时继续明确报错，不用无收益摘要冒充成功。

摘要请求根据窗口输出预留给出Unicode字符上限，要求密集事实、约束及未解决事项，省去
标题和重复铺陈。同一材料最多两次精简请求；不符合预算时保留原上下文。
若已有摘要挤占下一完整单元的空间，先按实际剩余空间精简摘要，再合并后文。
同一边界最多精简两次；保留首次输入中的已有用户原话，避免仅因空间不足丢掉它们。
不在客户端截断摘要，也不拆开问答或工具交换来掩盖预算问题。

覆盖范围内的旧图片只以摘要中的文字事实承接，后续请求不再发送对应像素。
本地聊天、归档与原图继续保留。未覆盖的图片及本次待发图片仍完整携带。

### 工具续答

只在一批工具调用全部返回、下一次模型请求尚未发出时压缩。当前问题及最近一组工具交换
始终保留，已执行工具不重复执行。完整历史覆盖 seq 与当前回复的工具批次覆盖分别记录。
同一条回复内可多次推进。摘要生成、归档和检查点提交成功后才继续请求模型。
正常结束、停止和失败均保留收到的正文、来源与公开检索记录。

同身份下仅续传未覆盖的协议交换；换模型、协议或凭据后使用公开参考资料。
已覆盖的签名、加密思考与工具载荷不会重新进入上下文。检查点不提升为系统指令。

### 持久化与兼容

会话 `metadata_json.context_compression` 使用检查点版本 2，保留摘要、覆盖 seq、原话的
源 seq 与文本、来源校验、修订号、时间和归档关联。工具中的检查点放在相应 AI 消息
`metadata_json.tool_compaction`，另有来源终点和已覆盖工具批次数。旧版检查点可继续读取，
下一次成功压缩时自然升级。数据库表结构保持兼容。

聊天、重试、上下文用量和摘要详情共用有效上下文读取。重试候选、编辑及继续聊天使用
各自既有原子提交路径。工具压缩提交在单一数据库线程内创建完整归档、保存图片关联及
检查点；重复提交同一修订不重复归档。失败回滚，旧保存快照不能覆盖更新的检查点。

导入导出携带公开摘要、原话位置与公开工具资料，校验覆盖范围并在导入后重新绑定校验。
导出不包含签名、密钥或可重放的私有工具状态。检查点不匹配时保留完整历史并停用摘要。

### 已确认的代码行为与本地证据

`context.cpp::summarize()` 使用现有 `streamModelRound()`，但只读取
`response_state.output` 和 `done`，忽略 `network_error` 中已有的错误、HTTP 状态和
请求标识。因此 HTTP 400／429／5xx、传输失败、协议不完整以及非正常 finish reason
均可能只显示“上下文压缩失败，请检查网络或模型配置；未发送本次消息”。这是一项
已确认的诊断缺陷，并不意味着所有失败都来自网络。

以现有 `build/host/libpenchat_core.a` 链接独立 C++14 探针，通过本机假 HTTP 服务验证：

| 模拟情况 | 底层结果 | 压缩结果 |
| --- | --- | --- |
| 正常正文、stop、DONE | done | 成功生成摘要 |
| HTTP 400，含明确错误正文 | network_error，保留 HTTP 400 和原始测试原因 | 仅通用失败文案，具体原因丢失 |
| 正文存在，finish_reason 为 length | network_error，回复未完成：length | 仅通用失败文案，不能使用截断摘要 |
| 仅 reasoning_content，没有正文 | done，但正文为空 | 仅通用失败文案，不能把思考当作摘要 |
| stop 后关闭连接，缺少 DONE，严格模式 | network_error，Stream ended before completion | 仅通用失败文案 |

| 正常结束，但返回 8,000 个本地估算 token，摘要预算为 4,096 | done | 报“模型生成的摘要未满足预算”，原上下文不提交 |

### Gemini 相关线索与尚未证实的原因

- 压缩明确使用 API 默认强度，清空 `effort_value`，不请求公开思考；这不等于禁用
  模型内部思考。Google 的 [OpenAI 兼容说明](https://ai.google.dev/gemini-api/docs/openai)
  表明不传 reasoning_effort 时使用模型默认思考级别／预算，部分模型不支持关闭。
  因此默认思考可能增加延迟；是否导致这次超时、空正文或输出限制，须由实际错误证明。
- 本地 `summaryBudget` 目前写在整理提示词中，再对结果做估算校验；当前 OpenAI 兼容
  请求体没有据此发送输出 token 上限。模型正常返回但未遵守提示长度时，压缩仍会失败。
  不应简单把摘要预算原样作为 Gemini 的总输出上限：Google 的
  [思考 token 与输出限制说明](https://ai.google.dev/gemini-api/docs/generate-content/thinking)
  说明思考会消耗输出预算，过小上限可能造成截断甚至空正文。
- 分批使用压缩模型本地 context_budget 的 75%，没有在该分批处统一收敛到已配置的
  max_input_tokens。实际端点上下文／输出能力、图片估算及用户预算不一致时有被拒绝的风险；
  目前没有该用户请求的证据，不能把它认定为已发生。
- 历史整理材料保留原 user／assistant 线角色，并只对 Anthropic 做统一 user 引用处理。
  探针确认本次末条为 assistant；某些兼容网关的角色／续写约束仍需核对。
  不将“Gemini 一律不接受末条 assistant”当作已确认事实。
- 当前只有 Responses、Chat Completions 和 Anthropic Messages；没有 Gemini 原生
  generateContent 协议。需核对用户选择的接口与实际地址，而非按模型名自动改 URL、
  协议、强度或 Provider。
